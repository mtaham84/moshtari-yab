# گزارش اجرای تسک P06.05: تسویه مبتنی بر نگاشت یکتا (mapping-based settlement)

## ۱. مشخصات تسک
- **شناسه:** P06.05
- **فاز:** ۶ — اعتبار، صف پایدار، ledger و retry
- **یافته‌های مبنا:** R31, R32
- **پیش‌نیازها:** P06.02, P06.03
- **فایل‌های تغییریافته:**
  - `apps/billing/settlement_service.py`
  - `apps/billing/tests/test_p06_05_settlement_mapping.py`

## ۲. خلاصه تغییرات
1. **حذف وابستگی به مکان‌نمای ناامن `MAX(id)` (رفع باگ R31):**
   - در معماری قبلی با استفاده از `SELECT MAX(id)` و کرسر سراسری، اگر تراکنشی با id کوچک‌تر دیرتر از تراکنش بعدی کامیت می‌شد، ردیف آن برای همیشه نادیده گرفته می‌شد یا کرش ورکر باعث شارژ تکراری می‌شد.
   - سرویس جدید `SettlementService` مستقیماً رکوردهای `CostAllocation` را بر اساس وضعیت `PENDING` و نگاشت یکتا در جدول `SettlementMapping` تسویه می‌کند.
2. **برقراری Idempotency کامل با نگاشت یک‌به‌یک (`OneToOneField`):**
   - هر تخصیص هزینه حداکثر می‌تواند دارای یک رکورد در `SettlementMapping` باشد.
   - اجرای دوباره تسویه یا کرش ورکر و تلاش مجدد هیچ شارژ اضافه بر کیف پول تحمیل نمی‌کند.
3. **پیوند اتمیک با رزرواسیون کیف پول (`WalletReservation`):**
   - در صورت وجود رزرو قبلی برای همان عملیات، تسویه از طریق `budget_svc.settle` مبلغ رزرو را با مصرف واقعی تطبیق داده و مانده را آزاد می‌کند و رکورد رزرو به نگاشت تسویه متصل می‌شود.
4. **توقف موارد نامشخص و خارج از سقف (`UNRESOLVED`):**
   - هزینه‌های نامشخص (`is_unknown=True`) به جای کسر خودکار یا نادیده‌گرفتن بدون صدا، در وضعیت `UNRESOLVED` نگهداری می‌شوند تا تحت حسابرسی قرار گیرند.

## ۳. شواهد تست و نتایج
- **فایل تست:** `apps/billing/tests/test_p06_05_settlement_mapping.py`
- **فرمان اجرا:**
  ```bash
  docker compose exec -T web python manage.py test apps.billing.tests.test_p06_05_settlement_mapping --keepdb
  ```
- **نتیجه:** ۵ تست در ۰.۱۷۷ ثانیه با موفقیت ۱۰۰٪ پاس شدند:
  1. `test_out_of_order_commit_settles_both_allocations_correctly`: اثبات این که تسویه با id بزرگ‌تر مانع از تسویه id کوچک‌تر پس از کامیت دیرهنگام نمی‌شود و هر دو ردیف دقیقاً یک‌بار تسویه می‌شوند.
  2. `test_retry_and_crash_idempotency_creates_zero_duplicate_charge`: اجرای دوباره تسویه شارژ دوم نمی‌سازد.
  3. `test_unresolved_cost_hold_does_not_debit_wallet`: نگهداری رویداد نامشخص به عنوان `UNRESOLVED` بدون کسر از کیف پول.
  4. `test_reservation_linking_and_settlement`: پیوند موفق نگاشت با رزرو فعال و کسر مبلغ واقعی.
  5. `test_batch_settlement_summary`: پردازش دسته‌ای و ارائه گزارش آماری دقیق.

## ۴. ریسک باقی‌مانده و روش بازگشت
- **ریسک باقی‌مانده:** صفر؛ سرویس به صورت ایزوله عمل می‌کند و کرسر قبلی همچنان برای داده‌های خواندنی حفظ شده است.
- **روش بازگشت (Rollback):** با حذف فایل `apps/billing/settlement_service.py`، سیستم به وضعیت پیشین بازمی‌گردد.
