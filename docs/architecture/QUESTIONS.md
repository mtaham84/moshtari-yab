# Questions and ambiguous intent

These are points where code or runtime convention does not establish product intent. The current behavior is recorded without choosing a preferred interpretation.

1. **Instagram has two separate collectors.** workers/ig_collector supports account seeds, comments, seller leads, local JSONL, and state (workers/ig_collector/worker.py:183-210, :491-541). instagram_discovery reads OpenCLI user/Explore posts, filters Persian captions, and writes its own archive/review files; it says it does not read comments or write to Django (instagram_discovery/cli.py:133-174). Are these two experiments meant to continue independently, or should one become the supported path? There is no Compose runner for either today (docker-compose.yml:28-128).
2. **Telegram heartbeat cadence differs by mode.** The live heartbeat task writes beat_ok on an interval even if the counter has not advanced (telegram_crawler/main.py:55-62); a no-live run writes one success beat at exit (:108-110). Should “last ok” mean the collector process is alive or that it archived at least one new message?
3. **Collector heartbeat schema is crawler-configured.** Shared heartbeat helpers use TG_DB_SCHEMA and create <schema>.collector_heartbeats (shared/collector_kit/heartbeat.py:14-18, :37-53); Telegram also declares collector_heartbeats in its schema file (telegram_crawler/schema.sql:7-17). Should heartbeat storage remain inside the configured crawler schema for X/Instagram as well?
4. **NE_DATABASE_URL and DATABASE_URL are aliases.** Engine and X ingest accept either (need_engine/config.py:32-41, x_ingest/__main__.py:19-28); Telegram also accepts TG_DATABASE_URL first (telegram_crawler/config.py:39-50). Which variable should deployment documentation treat as canonical?
5. **Retention wording and code differ in detail.** README says purge_retained_data --delete removes old Telegram/X source data and preserves opportunities/status/financial records (README.md:42-44). The command calls engine retention, panel opportunity scrubbing, panel X cleanup, and X SQLite state cleanup (apps/core/management/commands/purge_retained_data.py:40-49). Is the README phrase “old opportunity text/identity is scrubbed” the intended retained opportunity behavior, or should retained opportunities be described differently? Code review shows old source identity may be retained for opportunities with orders or CONTACTED/CONVERTED status; other affected opportunity text/metadata is scrubbed, and eligible customers may be anonymized (apps/discovery/retention.py:7-15; telegram_crawler/retention.py:476-564). Is that the intended preservation rule?
6. **Retention report stores whatever counts it parses.** It runs the purge command without --delete, parses stdout lines as counts, and writes timestamp/exit code (scripts/retention_report.py:12-39). Should report consumers distinguish count-only mode from actual deletion in the panel? The current shape does not store a mode field.
7. **X collector CLI and engine settings overlap.** X_QUERY_* variables build collection queries (workers/x_collector/intent_queries.py:103-138), while NE_X_* control engine-side filtering and matching (need_engine/config.py:110-145). Some names in .env.example are not read in the Python files scanned, including X pause/suggest/score/thread options; their intended consumer is unclear.
8. **Instagram settings and run inputs overlap.** The worker constructor reads daily cap, sleep, retries, and state settings (workers/ig_collector/worker.py:193-201), while seed JSON also carries per-run limits and comment policy (workers/ig_collector/worker.py:143-181). Which source should be authoritative when both specify a limit?
9. **The Django admin panel and engine have two state/status mechanisms.** need_engine stores its heartbeat in its own kv table (need_engine/engine.py:688-691); collectors use crawler.collector_heartbeats (shared/collector_kit/heartbeat.py:37-82); Django apps.billing.services.heartbeat writes operational state through the panel database (apps/billing/services.py:139-145). Should these remain separate because they describe different process health, or should the dashboard normalize them?
10. **xray contains both an optional proxy container and a local proxy-management utility.** Compose starts the Xray image only with proxy profile and mounts xray/config.json (docker-compose.yml:120-128); xray/proxy_switcher.py has CLI, daemon, and systemd installation paths (:642-851). Is the local utility expected to manage the same config used by Compose?
11. **The secondary worktree may be old, but that is unverified.** git worktree list --porcelain reports .worktrees/x-need-engine on feature/x-need-engine at commit 399527e9c4403a46f6490df0697e151a7d256e96. Is it still an active work area? Do not remove it based only on its directory name.

## Documentation mismatches

- .env.example describes need_engine as the only analysis pipeline, but Instagram has two independent analysis/collection toolchains. Evidence: workers/ig_collector/worker.py:242-465 and instagram_discovery/cli.py:87-174. Whether “analysis pipeline” refers only to connected production processing is ambiguous.
- README presents docker compose up -d --build as PostgreSQL + panel + sync + engine + Telegram crawler (README.md:112-114). Compose confirms those default services (docker-compose.yml:28-88); X and retention reporting require profiles (:90-118), and Instagram is not declared there (:28-128).
- .env.example documents names without direct Python readers. Some are used by external tools or profiles, and helper-based reads require following the helper implementation. CONFIG.md separates these cases; third-party CLI environment handling is not statically verifiable.
- docs/IG_COLLECTION_ANALYSIS.md describes the Instagram experiment and policies; actual OpenCLI discovery currently writes separate post/review JSONL and explicitly does not read comments or Django (instagram_discovery/cli.py:133-174).

Items marked unverified reflect unavailable filesystem access or behavior that static code inspection cannot establish. The local retention code above was inspected; runtime effects against a production database were not exercised.
