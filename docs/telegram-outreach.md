# ارسال دستی پیام تلگرام

در جزئیات فرصت تلگرام، زیر پیش‌نویس و در فهرست فرصت‌ها زیر متن پیشنهادی،
دکمهٔ «ارسال پیام» قرار دارد. متن فعلی نمایش‌داده‌شده (در جزئیات، پس از ویرایش)
بعد از تأیید فروشنده در صف PostgreSQL ثبت می‌شود. هیچ لید جدیدی خودکار پیام نمی‌گیرد.

## حساب فرستنده و محدودیت‌ها

- تمام پیام‌ها از همان حساب کاربری متصل به `crawler` می‌روند؛ نه حساب شخصی هر فروشنده.
- فقط پیام خصوصی به کاربر تلگرام؛ پاسخ عمومی به گروه یا ارسال در X/Instagram اضافه نشده است.
- فقط برای مخاطبانی استفاده کنید که انتظار دریافت پیام دارند. محدودیت‌های تلگرام و
  حریم خصوصی مخاطب همچنان برقرارند؛ فاصلهٔ ارسال تضمین جلوگیری از محدودیت نیست.
- حساب باید به entity مخاطب دسترسی داشته باشد. اگر شناسه در سشن قابل حل نباشد،
  نام کاربری ذخیره‌شده تنها در صورت تطبیق شناسهٔ عددی پذیرفته می‌شود.
- تغییر مالک نام کاربری، گروه/کانال، ربات و حساب حذف‌شده، مقصد قابل ارسال نیستند.
- یک پیام برای هر فرصت؛ کلیک تکراری، تب دوم و refresh پیام جدیدی نمی‌سازند.
- ارسال مجدد، پیام گروهی، زمان‌بندی کمپین و اتصال حساب مستقل فروشنده خارج از این تغییرند.
- ثبت «ارسال شد» یعنی تلگرام ارسال را تأیید کرده؛ به معنی خوانده‌شدن نیست.

## استقرار با Docker

ابتدا از دیتابیس و volume سشن نسخهٔ پشتیبان بگیرید. سپس patch را روی نسخهٔ مبنا
`1745620edabf212865a9d8494d06f442b047f01c` یا نسخهٔ سازگار مخزن اعمال کنید:

```bash
git apply --check /path/to/telegram-send-button.patch
git apply /path/to/telegram-send-button.patch
```

اگر بررسی اول شکست خورد، patch را به اجبار اعمال نکنید؛ اختلاف نسخه را بررسی کنید.

تنظیم‌ها در `.env` (پیش‌فرض‌ها نیز همین مقادیرند):

```dotenv
TG_OUTREACH_ENABLED=true
TG_OUTREACH_INTERVAL_SECONDS=60
```

سرویس دیتابیس را روشن نگه دارید. برای اینکه کد قدیمی هنگام migration روی برنامهٔ
جدید کار نکند، سرویس‌های برنامه را متوقف و سپس imageها را بازسازی کنید:

```bash
docker compose stop crawler engine sync web
docker compose up -d --build web crawler engine sync
docker compose logs --tail=100 -f web crawler
```

`web` طبق entrypoint موجود، migration `0019_telegram_outbound_message` را در شروع
اجرا می‌کند. قبل از دسترس‌پذیر کردن پنل، لاگ migration و وضعیت سرویس‌ها را بررسی کنید.
فایل‌های static هم در image جدید ساخته می‌شوند. سشن قبلی باقی می‌ماند؛
`docker compose down -v` اجرا نکنید.

فقط **یک نمونهٔ crawler** اجرا کنید. worker ارسال از همان client متصل استفاده
می‌کند و پردازش مستقل دیگری فایل سشن را باز نمی‌کند. فراخوانی‌های ORM به thread
منتقل می‌شوند و انتظار صف، مانیتورینگ زنده را متوقف نمی‌کند.

## وضعیت‌ها و خطا

- «در صف ارسال»: درخواست ثبت شده؛ crawler باید روشن و واردشده باشد.
- «در حال ارسال»: worker درخواست را برداشته است.
- «ارسال شد»: شناسهٔ پیام از تلگرام دریافت شده و فرصت جدید/بررسی‌شده، «تماس گرفته شده» می‌شود.
- «ارسال ناموفق»: مقصد قابل دسترسی نیست، فرصت بسته شده یا تلگرام ارسال را رد کرده است.
- «نتیجهٔ ارسال نامشخص»: ممکن است پیام رسیده باشد. ابتدا در تلگرام بررسی کنید؛
  برای جلوگیری از پیام تکراری، تلاش مجدد خودکار و دکمهٔ ارسال دوباره وجود ندارد.

FloodWait زمان تلاش بعدی را در دیتابیس نگه می‌دارد و worker را منتظر می‌گذارد.
شناسهٔ `random_id` برای همان پیام ثابت است. درخواست‌های SENDING که بیش از ده
دقیقه بدون نتیجه مانده‌اند UNKNOWN می‌شوند، نه اینکه کورکورانه دوباره ارسال شوند.
پاک‌سازی retention متن و شناسهٔ مقصد outbox را نیز پاک می‌کند، ولی رکورد جلوگیری
از ارسال تکراری باقی می‌ماند. طبق روال موجود پروژه، پاک‌سازی واقعی را با workerهای
متوقف‌شده انجام دهید.

برای توقف ارسال: `TG_OUTREACH_ENABLED=false` را تنظیم و `web` و `crawler` را
با `docker compose up -d --force-recreate web crawler` بازسازی کنید.
پیام‌های PENDING در صف باقی می‌مانند و با فعال‌سازی دوباره قابل پردازش‌اند.

## تست

```bash
docker compose run --rm web python manage.py test apps.discovery.tests_telegram_outbox
```

تست‌ها به PostgreSQL تست دسترسی می‌خواهند، اما از حساب، شبکه یا API واقعی تلگرام
استفاده نمی‌کنند. پیش از استفادهٔ واقعی، با حساب و مخاطب آزمایشیِ دارای رضایت،
دکمه، دریافت متن و نتیجهٔ ارسال را به‌صورت end-to-end بررسی کنید.
